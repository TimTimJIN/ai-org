# ai-org の UI/UX デザイン指針

UI/UX 担当（現在は Codex。ほかの AI が画面を変える場合も同じ）が、画面を作る・変える前に読む。
画面の変更は、この指針のチェックリストで自己確認し、最後の「学習記録」に学びを1件以上足す。

## 1. 利用者と画面の役割

- 利用者：AI に開発を任せる個人。プログラムの内部（編集権、claim、snapshot など）は知らなくてよい。
- 案件画面（`hub/hub_ui.py`）の役割：「いまどの案件が、誰の番で、私は次に何を押せばよいか」を3秒で分からせる。
- 画面の成否は「迷わず次の操作を押せたか」で測る。説明文の多さ・機能の多さでは測らない。

## 2. 原則（判断に迷ったらこの順で優先）

1. **主役は1つ**：1画面・1領域に、強調する操作（主ボタン）は1つだけ。ほかは普通ボタンか、文字リンク・メニューに下げる。いま押すべき操作が主ボタンになるよう、状態に合わせて切り替える。
2. **状態は見える場所に、言葉と色の両方で**：案件の状態（作業中・停止中・レビュー待ちなど）は案件名のすぐ横にバッジで出す。色だけに頼らず、必ず文字を添える（色覚の多様性への配慮）。一覧でも各案件の状態を出し、クリックしなくても分かるようにする。
3. **利用者の言葉で書く**：内部用語は画面に出さない。出す必要がある場合は言い換える（例：「編集権」→「編集権を持つAI（作業中とは限らない）」、「claim で取得」→ 表示しない、「snapshot」→「レビュー用コピー」）。担当予定と編集権は意味が違うので、言い換えても混ぜない。ID・パスなどの技術情報は「詳細」に畳む（段階的開示）が、復旧（recover）に使う編集権IDなどは「詳細」から必ずたどれるようにする。
4. **注意書きは、操作の近くに短く、重ねない**：操作の可否や限界にかかわる注意（「自動送信しない」「即時通知・強制停止ではない」など）は、該当する操作の近くに常に残す。削ってはいけない。下部のお知らせ欄は操作のたびに上書きされるので、そこへ移すと消える。直してよいのは、言い回しを短くそろえることと、同じ趣旨の注意の重複だけ。重複が多いと、本当に重要な警告が読まれなくなる。
5. **近いものは近くに、違うものは離す**（近接と余白）：関係の強い要素は 8px 以内、別のまとまりは 16〜24px 離す。枠線を増やすより余白で区切る。
6. **操作の結果を必ず返す**：押した後、何が起きたか（コピーした、保存した、まだ送っていない）をその場で示す。失敗時は「何が起きたか＋次にどうすればよいか」を書く。
7. **取り消せない操作・未保存の内容は守る**：確認ダイアログは本当に失うものがある時だけ出す。確認の文はボタン名を動詞にする（「破棄して閉じる」／「戻る」。「はい／いいえ」は避ける）。
8. **一貫性**：同じ意味の操作は、同じ名前・同じ位置・同じ見た目にする。

9. **画面の自動更新で、利用者の操作を奪わない**：案件画面は1.5秒ごとに状態を読み直す。選択・入力中の文字・フォーカス・スクロール位置を変えない。
10. **キーボードでも使える**：フォーカスの位置が見えること（WCAG 2.4.7）。ダイアログは Enter で主の操作、Esc で閉じる。

参考にした基準：Nielsen の10のユーザビリティ原則（状態の可視化、実世界との一致、一貫性、エラー防止、記憶より認識、最小限の美しさ）、WCAG 2.2、デジタル庁デザインシステム（DADS。WCAG 2.2 を参照。JIS X 8341-3:2016 は WCAG 2.0 相当）。

## 3. 基準値（デザイントークン）

色はすべて WCAG のコントラスト比を計算して確かめた値。文字は 4.5:1 以上（18pt 以上、または 14pt 以上の太字は 3:1 以上でよい）、入力欄の枠などの部品の境界は 3:1 以上（WCAG 1.4.3／1.4.11）。

| 用途 | 色 | 背景 | 比 |
|---|---|---|---|
| 本文 | `#172b42` | 画面背景 `#f4f6fa` | 13.3 |
| 補足文 | `#526579` | `#f4f6fa`／白 | 5.6／6.0 |
| 主ボタン（背景） | `#0b5cad`、文字は白 | — | 6.7 |
| 選択中の行 | 文字 `#0b5cad` | `#e8f1fb` | 5.9 |
| 入力欄・カードの境界線 | `#7b8794` | 白／`#f4f6fa` | 3.7／3.4 |
| 状態：進行中・完了（緑） | `#1d6b3a` | `#e6f4ea` | 5.8 |
| 状態：待ち・要確認（橙） | `#8a4b00` | `#fdf1e1` | 6.1 |
| 状態：停止・エラー（赤） | `#a1261b` | `#fdecea` | 6.5 |

避ける組み合わせ（現状で使われているもの）：

- 一覧の選択行（ウィンドウが前面にないとき）白文字／`#9e9a91`：2.8（不足）
- clam 既定の境界線 `#9e9a91`／白：2.8（入力欄・カードの枠としては不足）

文字（Yu Gothic UI）：

- 画面見出し 18pt 太字、案件名 14pt 太字、領域見出し 11pt 太字、本文・ボタン 10〜11pt。これ以上サイズを増やさず、太さと色で差をつける。
- 本文の行の高さはフォントサイズの 1.5 倍以上（DADS の決まり）。tkinter の `Text` は、折り返した行の間を `spacing2` で、段落の前後を `spacing1`／`spacing3` で足す。
- 日本語の長文は1行 35〜45 文字程度が読みやすい。`wraplength` で行を折る。固定値の `wraplength` はウィンドウ幅に追従しないので、`<Configure>` で幅に合わせて更新する。

余白：4 の倍数（4・8・12・16・24）だけを使う。画面の外周 16、まとまり同士 16〜24、まとまりの中 8。

## 4. tkinter（ttk）での実装メモ

- テーマは `clam`。主ボタンは `Primary.TButton` スタイルを作り、`style.map` で `active`（ホバー）・`disabled` の色も必ず決める。
- 一覧（Treeview）の選択色は `style.map("Treeview", background=[...], foreground=[...])` で、ウィンドウが前面かどうか（clam の `background` 状態）に関係なく同じ色にする。`style.map` は状態の組をまるごと置き換えるので、`disabled` など既存の組も一緒に書く。
- 状態バッジは `tk.Label`（背景色を持てる）で作り、文字を必ず入れる。
- Windows の拡大表示（150% など）で文字がぼやけないよう、DPI 対応の宣言を検討する（`ctypes.windll.shcore.SetProcessDpiAwareness(1)`）。`tk.Tk()` より前に呼び、使えない環境や設定済みで失敗するので try で包む。宣言すると、固定ピクセル値（`rowheight`、`wraplength`、`geometry`、`minsize`）と pt 指定の文字の比率が変わり、文字が切れることがあるので、画面全体を確認する。
- tkinter は読み上げソフト（スクリーンリーダー）への対応が弱い。重要な情報は画像や色だけにせず、文字として選べる・コピーできる形でも出す。Windows のハイコントラスト表示では独自の色が反映されないことがあるので、色だけに意味を持たせない。
- 新しい画面・部品を作る時は、最小サイズ（現在 920×620）でも主ボタンと状態が見えることを確かめる。

## 5. 変更前後のチェックリスト

画面を変えたら、変更前と変更後のスクリーンショットを撮り（テスト用データフォルダーで起動する）、次を確かめる。

- [ ] 初めて見た人が、3秒で「次に押すもの」を指させるか（主ボタンが1つだけか）
- [ ] 案件の状態が、案件名の近くと一覧に、文字付きで出ているか
- [ ] 内部用語・ID・パスが、詳細を開かなくても目に入る位置に残っていないか
- [ ] 同じ趣旨の注意書きが2か所以上に出ていないか（減らすときは、操作の近くに常に出る注意を残し、結果メッセージの側を短くする）
- [ ] 文字のコントラスト 4.5:1、部品の境界 3:1 を満たすか（色を変えた時は計算する）
- [ ] 押せないボタンが押せるボタンと区別でき、なぜ押せないかが分かるか
- [ ] 最小ウィンドウサイズと、Windows の拡大表示 150% で崩れないか
- [ ] キーボードだけ（Tab・Enter・Esc）で主な操作ができ、フォーカスの位置が見えるか
- [ ] 1.5秒ごとの自動更新で、選択・入力中の文字・スクロール位置が変わらないか
- [ ] 操作の限界にかかわる注意（自動送信しない、即時通知ではない等）が、該当操作の近くに残っているか
- [ ] 操作の後に結果のメッセージが出るか。エラー文に「次にどうするか」があるか
- [ ] 既存のテスト（`cd hub && python -m unittest discover -p "test_*.py"`）が通るか

## 6. 現在の案件画面の診断（2026-11-20、Claude Code）

テスト用データで起動して撮影し、上の原則と基準値で確かめた。改善は優先度の高い順。

**対応済み（2026-11-20）**：優先「高」の3件と、状態バッジ（中）。次の操作に合うボタンだけを主ボタン（青）にする、一覧の各行に状態（作業中・開始待ち・停止中・停止要求中・再開待ち・要確認）を文字で出す、選択色と枠線の色を固定、案件名の横に色つきの状態バッジ、一時停止・再開をバッジと同じ行へ、「＋ 案件を作る」を一覧の上へ、タブ本文の行間を広げた。残りの「中」「低」は未対応。既知の制約：一覧の状態は1.5秒ごとに全案件を読み直す（案件が数十件を超えたら間引く）。最小幅では長い案件名が多くの行に折り返す。

## 7. 学び続ける仕組み

- UI を変える作業では、作業の最初にこの文書を読み、終わりに次の「学習記録」へ1件以上足す（何を見て・何を学び・どこに使ったか）。
- 外部の基準（WCAG、DADS、NN/g、各OSのガイドライン）を新しく読んだら、出典と要点を記録する。古くなった項目は消さずに「訂正」を書き足す。
- 利用者の画面への指摘（feedback）は、個別の修正で終わらせず、原則やチェックリストに一般化できないか考えて反映する。
- レビューでは、Claude と Gemini に、スクリーンショットとこの文書のチェックリストを渡して評価を受ける。
